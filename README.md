# AI Scheduler

할 일을 자꾸 미루는 사람을 위한 AI 일정 관리 서비스입니다. 평소 말투로 일정을 입력하면 AI가 정리하고, 못 한 일은 AI가 다시 넣을 시간을 제안하고, 한 주의 기록을 보고 미루는 패턴을 알려줍니다.

> 🚧 현재 개발 중입니다. 진행 상황은 아래 로드맵에서 확인할 수 있습니다.

## 만든 이유

해야 할 일을 알고 있어도 정해진 시간이 없으면 계속 미루게 되는 문제를 직접 겪었습니다. 반대로 PT나 운동처럼 날짜와 시간이 정해진 약속은 잘 지킨다는 걸 알게 되었고, 일상의 할 일도 약속처럼 관리해주는 도구를 직접 만들어 매일 사용하면서 개선해 나가고 있습니다.

## 주요 기능

### AI가 맡는 기능

- **자연어 일정 입력**: "다음 주 화요일 오후 3시 치과"처럼 입력하면 AI가 날짜, 시간, 할 일로 해석해 입력 칸을 채워주고, 사용자가 확인하고 고친 뒤 저장합니다.
- **미룬 일정 재조정 제안**: 완료하지 못한 일정이 생기면, AI가 앞으로의 일정과 겹치지 않는 시간을 찾아 다시 넣을 시간을 제안합니다.
- **주간 회고 리포트**: 한 주의 완료 기록을 보고 "수요일 저녁 일정이 자주 미뤄진다"처럼 미루는 패턴을 찾아 조언합니다.
- **큰 일 쪼개기**: "이력서 완성"처럼 막연한 일을 날짜가 붙은 작은 일정으로 나눠줍니다.

### 규칙으로 처리하는 기능

- **아침 알림**: 매일 아침 그날의 일정을 알려줍니다.
- **완료 체크**: 일정의 진행 여부를 기록합니다.
- **주간 달성률**: 완료 기록으로 달성률을 계산합니다.

알림, 완료 체크, 달성률 계산처럼 정해진 규칙으로 충분한 기능에는 AI를 쓰지 않고, 상황을 판단하거나 기록을 해석해야 하는 기능에만 AI를 사용합니다.

## 실행 방법

백엔드와 프론트엔드를 각각 다른 터미널에서 실행합니다.

**Backend**

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
uvicorn main:app --reload
```

서버 실행 후 http://127.0.0.1:8000/docs 에서 API를 확인할 수 있습니다.

**Frontend**

```bash
cd frontend
npm install
npm run dev
```

http://localhost:5173 에서 화면을 확인할 수 있습니다.

## API

| Method | Endpoint | 설명 |
|---|---|---|
| POST | `/schedules` | 일정 추가 |
| GET | `/schedules` | 일정 목록 조회 (날짜순) |
| PATCH | `/schedules/{schedule_id}` | 일정 일부 수정 (완료 체크 포함) |
| DELETE | `/schedules/{schedule_id}` | 일정 삭제 |
| POST | `/schedules/parse` | 자연어 문장을 AI로 해석해 일정 형태로 반환 (저장하지 않음) |
| GET | `/schedules/overdue` | 날짜가 지났는데 완료하지 않은 일정 조회 |
| POST | `/schedules/{schedule_id}/suggest` | 미룬 일정을 다시 할 날짜와 시간을 AI가 이유와 함께 제안 (검증 후 반환, 저장하지 않음) |
| GET | `/stats/weekly` | 이번 주(월~일, 한국 시간 기준) 일정 수, 완료 수, 달성률 조회 |

일정 추가 요청 예시:

```json
{
  "title": "PT",
  "scheduled_date": "2026-10-29",
  "scheduled_time": "14:00"
}
```

자연어 해석 요청과 응답 예시 (2026-11-19 기준):

```json
// 요청
{ "text": "내일 오후 2시 PT" }

// 응답
{
  "title": "PT",
  "scheduled_date": "2026-11-20",
  "scheduled_time": "14:00:00"
}
```

재조정 제안 응답 예시:

```json
{
  "scheduled_date": "2026-11-23",
  "scheduled_time": "10:00:00",
  "reason": "월요일 오전 10시는 주중에 집중하기 좋은 시간이라 미뤄둔 업무를 처리하기에 적당해요. 이번 주말 일정과도 겹치지 않아요."
}
```

주간 달성률 응답 예시:

```json
{
  "start": "2026-11-23",
  "end": "2026-11-29",
  "total": 5,
  "done": 3,
  "rate": 60
}
```

## 개발 기록

개발하면서 겪은 문제와 해결 과정을 기록합니다.

**패키지를 설치했는데 `ModuleNotFoundError`가 발생**
가상환경이 꺼진 터미널에서 `pip install`을 실행해 패키지가 다른 위치에 설치된 것이 원인이었습니다. 가상환경을 활성화한 뒤 `python -m pip install`로 설치해 현재 실행 중인 파이썬 환경에 확실히 설치되도록 해결했습니다.

**모델 필드 이름을 `date`, `time`으로 지으면 생기는 충돌**
파이썬의 `date`, `time` 타입과 필드 이름이 겹치면 타입을 인식하지 못하는 문제가 생길 수 있어, `scheduled_date`, `scheduled_time`으로 이름을 구분했습니다.

**입력용 모델(`ScheduleCreate`)을 따로 둔 이유**
SQLModel의 테이블 모델(`table=True`)은 입력 데이터를 검증하지 않아, `"2026-10-29"` 같은 문자열이 날짜로 변환되지 않습니다. 입력용 모델을 분리해 검증과 타입 변환을 거치도록 하고, `id`, `is_done`, `created_at`처럼 서버가 정해야 할 값은 사용자가 보낼 수 없도록 했습니다.

**시간대 정보 없는 datetime 저장 에러**
`datetime.now()`로 만든 생성 시각에 시간대 정보가 없어 저장이 거부되었습니다. `datetime.now(timezone.utc)`로 UTC 기준 시각을 저장하도록 수정했습니다. 배포 서버는 보통 UTC 기준으로 동작하기 때문에, 저장은 UTC로 통일하고 표시나 알림 시점에 한국 시간으로 변환하는 방식으로 알림 시각이 어긋나는 문제를 미리 방지했습니다.

**일정 수정을 PUT이 아닌 PATCH로 설계**
완료 체크처럼 일부 값만 바꾸는 경우가 많아 PATCH를 사용했습니다. `model_dump(exclude_unset=True)`로 사용자가 실제로 보낸 값만 반영해, 보내지 않은 필드가 빈 값으로 덮어써지는 문제를 막았습니다. 존재하지 않는 일정을 수정하거나 삭제하면 404를 반환하도록 예외 처리도 추가했습니다.

**프론트엔드에서 백엔드 호출 시 CORS 차단**
프론트엔드(localhost:5173)와 백엔드(127.0.0.1:8000)의 주소가 달라 브라우저가 요청을 막았습니다. FastAPI에 `CORSMiddleware`를 추가해 개발용 프론트엔드 주소에서 오는 요청만 허용하도록 설정했습니다.

**시간 입력 중 값이 초기화되는 문제 (제어 / 비제어 컴포넌트)**
`<input type="time">`에 `value={time}`을 연결한 제어 컴포넌트로 만들었더니, 분을 입력하는 도중 오전/오후와 시가 초기화되고 클릭으로 고른 시간도 사라졌습니다. 시간 입력칸은 모든 칸이 채워지기 전까지 브라우저가 값을 빈 문자열로 취급하는데, 화면이 다시 그려질 때 리액트가 그 빈 값을 입력칸에 덮어쓴 것이 원인이었습니다. 시간 입력칸만 `value`를 제거한 비제어 컴포넌트로 바꾸고, 제출 후에는 `e.target.reset()`으로 폼을 초기화하도록 해결했습니다.

**시간이 저장되지 않는 문제 (`onchange` 오타)**
리액트는 이벤트 속성을 카멜 케이스(`onChange`)로만 인식하는데, `onchange`로 작성해 이벤트가 조용히 무시되었습니다. `console.log`로 전송 직전 값을 확인해 프론트엔드에서 값이 비어 있다는 것을 찾았고, `onChange`로 수정해 해결했습니다.

**화면에 시간이 초 단위까지 표시되는 문제**
백엔드가 시간을 `23:13:05.929000` 형태로 반환해, 화면 표시용 `formatTime` 함수로 시와 분만 보여주도록 했습니다. 표시 형식을 함수 하나로 분리해 이후 "오후 11:13"처럼 형식을 바꿀 때도 한 곳만 수정하면 되도록 했습니다.

**AI 해석과 저장을 분리한 설계**
AI는 날짜나 시간을 잘못 해석할 수 있어, `/schedules/parse`는 해석 결과만 반환하고 저장하지 않도록 했습니다. 사용자가 결과를 확인한 뒤 기존 `POST /schedules`로 저장하는 흐름으로, 잘못된 일정이 그대로 저장되는 것을 막습니다.

**"내일", "다음 주 화요일" 같은 상대 날짜 처리**
AI는 오늘이 언제인지 알지 못하므로, 요청마다 한국 시간(`Asia/Seoul`) 기준 오늘 날짜와 요일을 시스템 프롬프트에 함께 보냅니다. 서버가 UTC로 동작하더라도 한국 날짜 기준으로 계산됩니다.

**AI 응답을 그대로 믿지 않고 검증**
AI의 답은 결국 문자열이므로, `json.loads`로 변환한 뒤 `ScheduleCreate` 모델로 한 번 더 검증합니다. 형식이 맞지 않으면 422 에러와 함께 AI의 실제 응답을 보여주고, 응답이 코드 블록으로 감싸져 오는 경우에도 처리되도록 했습니다.

**API 키를 찾지 못하는 에러**
`api_key = os.getenv`처럼 괄호 없이 함수 자체를 변수에 담아 키를 불러오지 못했고, 그 값을 클라이언트에 넘겨주지도 않았습니다. Anthropic 클라이언트가 `ANTHROPIC_API_KEY` 환경 변수를 자동으로 읽는다는 점을 활용해 해당 코드를 제거하고, `load_dotenv()`를 클라이언트 생성보다 먼저 호출하도록 정리했습니다. 키 값은 `.env`에만 두고 코드에는 남기지 않습니다.

**응답의 첫 블록이 텍스트가 아닌 문제 (`ThinkingBlock`)**
Claude의 응답은 여러 블록의 목록으로 오는데, 첫 번째 블록이 답변 전 사고 과정(thinking)이어서 `content[0].text`에서 에러가 났습니다. 블록을 순서가 아닌 `type == "text"`로 골라내도록 바꾸고, 사고 과정이 토큰을 사용하는 점을 고려해 `max_tokens`를 늘렸습니다.

**함수 호출 괄호 누락 (`.strip` vs `.strip()`)**
괄호를 빠뜨려 공백을 제거한 결과가 아닌 함수 자체가 `json.loads`에 전달되었습니다. 에러에 `function`이나 `method` 같은 예상치 못한 타입이 보이면 괄호 누락부터 확인하는 습관을 들였습니다.

**가상환경이 꺼진 채 서버를 실행**
에러 경로가 `.venv`가 아닌 시스템 파이썬(3.11)으로 나타나 가상환경이 활성화되지 않았다는 것을 발견했습니다. 패키지가 `requirements.txt`에 누락되는 문제로 이어질 수 있어, 서버 실행 전 `(.venv)` 표시를 확인하도록 했습니다.

**프로젝트 방향 전환: AI를 쓸 곳과 쓰지 않을 곳 구분 (2026년 11월)**
처음에는 자연어 일정 입력, 아침 알림, 완료 체크, 달성률 통계를 주요 기능으로 기획했습니다. 기능을 다시 점검해보니 AI가 실제로 쓰이는 곳은 입력 문장을 날짜와 시간으로 바꾸는 부분 하나뿐이었고, 나머지는 AI 없이도 구현할 수 있는 기능이었습니다. "이 프로젝트에 AI가 꼭 필요한가?"라는 질문에 스스로 답하기 어렵다는 것을 깨닫고, 프로젝트의 출발점인 "할 일을 알면서도 미루는 문제"로 돌아가 방향을 다시 잡았습니다.

AI를 쓸지 정하는 기준은 "정해진 규칙으로 답이 나오는가"입니다. 알림 시간 계산, 완료 여부 기록, 달성률 계산처럼 규칙으로 충분한 기능은 코드로 처리합니다. 반대로 못 한 일을 언제 다시 하는 것이 현실적인지 판단하는 일, 한 주의 기록에서 미루는 패턴을 찾아 해석하는 일, 막연한 일을 작은 단계로 나누는 일처럼 상황을 보고 판단해야 하는 기능에만 AI를 사용합니다. 예를 들어 달성률 숫자는 코드로 계산하고, 그 숫자를 해석해 조언하는 부분만 AI가 맡습니다.

AI의 판단이 틀릴 수 있다는 원칙도 유지합니다. 자연어 해석과 마찬가지로, AI가 제안한 재조정 시간은 기존 일정과 겹치지 않는지 코드로 다시 검증하고, 최종 결정은 사용자가 내리도록 설계합니다.

**AI 해석 결과를 입력 칸에 채우는 방식으로 변경**
처음에는 AI 해석 결과를 별도의 미리보기로 보여주고 저장 버튼을 누르는 방식이었는데, 결과가 틀리면 취소하고 처음부터 직접 입력해야 했습니다. 해석 결과를 직접 입력 칸에 채워주도록 바꿔, 사용자는 틀린 부분만 고친 뒤 추가하면 됩니다. "AI는 초안을 만들고 최종 결정은 사람이 한다"는 원칙을 화면에 반영했고, AI가 응답하지 않을 때도 같은 칸에 직접 입력할 수 있습니다.

**비제어 컴포넌트에 값을 넣기 위한 `useRef`**
시간 입력칸은 앞선 문제로 `value`를 연결하지 않은 비제어 컴포넌트라, 상태만 바꿔서는 AI가 해석한 시간이 칸에 표시되지 않았습니다. `useRef`로 입력칸을 직접 가리켜 값을 넣었고, AI가 주는 `14:00:00` 형식은 기존 `formatTime` 함수로 `14:00`으로 바꿔 넣었습니다.

**날짜 기본값을 오늘로 설정할 때의 시간대 함정**
흔히 쓰이는 `new Date().toISOString().slice(0, 10)`은 UTC 기준이라 한국 시간 오전 9시 이전에는 어제 날짜가 나옵니다. 현지 시간 기준으로 연, 월, 일을 직접 조합하는 `getToday` 함수를 만들어 해결했습니다.

**직접 써보다 발견한 버튼 이름 문제**
AI 해석 결과를 입력 칸에 채우는 방식으로 바꾼 뒤에도 버튼 이름이 "AI로 추가"로 남아 있어, 직접 사용하면서도 이 버튼을 누르면 저장될 것이라 착각했습니다. 백엔드 로그에 해석 요청(`POST /schedules/parse`)만 있고 저장 요청(`POST /schedules`)이 없는 것을 보고 저장 단계에서 멈췄다는 것을 확인했습니다. 화면을 다시 보니 미리보기 코드를 지우면서 직접 입력 폼까지 함께 삭제되어 추가 버튼이 없었고, 폼을 복구한 뒤 버튼 이름도 실제 동작에 맞게 "AI로 채우기"로 바꿨습니다. 기능이 바뀌면 화면의 문구도 함께 점검해야 한다는 것을 배웠습니다.

**미룬 일정 재조정 제안: AI는 제안하고 코드는 검증한다**
완료하지 못한 일정과 앞으로 일주일의 일정을 데이터베이스에서 꺼내, AI가 읽기 좋은 목록 문장으로 정리해 전달합니다. AI는 데이터베이스를 직접 볼 수 없으므로 판단에 필요한 정보를 서버가 골라서 건네는 구조입니다. AI의 제안은 그대로 반환하지 않고, 형식을 모델로 검증한 뒤 코드로 두 가지를 다시 확인합니다. 지금보다 이전 시간을 제안하면 422, 이미 저장된 일정과 같은 시각이면 409 Conflict를 반환합니다. 예전 데이터에 초 단위 시간이 섞여 있어 비교할 때는 초를 제외합니다. 사용자가 제안을 수락하면 기존 `PATCH` API로 날짜와 시간만 바꾸므로 저장용 API를 새로 만들지 않았습니다.
현재 한계: 일정에 소요 시간 정보가 없어, 14시 일정이 있을 때 14시 30분 제안은 겹친다고 판단하지 못합니다. 같은 시각만 막고 있으며 이후 개선할 예정입니다.

**AI 호출 공통 함수 분리**
자연어 해석과 재조정 제안 모두 "AI 호출 → 텍스트 블록 선택 → 코드 블록 표시 제거 → JSON 변환"이 필요해, `call_ai_json` 함수로 분리했습니다. 새 AI 기능을 추가할 때 프롬프트와 검증 로직만 작성하면 됩니다.

**에러 메시지에 실패 이유를 담아 오타를 찾은 경험**
AI 제안이 정상 형식인데도 검증에 실패했습니다. 처음에는 AI 응답만 에러 메시지에 보여줬는데, `except ValueError as e`로 검증 실패 이유를 함께 보여주도록 바꾸자 검사 함수에 AI 응답(`data`)이 아닌 `date` 타입이 전달되고 있다는 것이 드러났습니다. `date`는 실제로 import된 이름이라 "정의되지 않음" 에러 없이 조용히 잘못된 값이 들어간 경우였습니다. 이후 에러 메시지에는 "무엇이 왜 틀렸는지"를 담도록 하고 있습니다.

**프롬프트 수정 후 기존 동작 재확인**
"내일 오전 10시 강아지 산책"을 직접 입력 칸에 넣어 문장 그대로 일정 이름이 된 경우가 있어, 직접 입력 칸의 안내 문구를 "할 일 이름만 (예: PT)"로 바꾸고, AI 프롬프트에도 할 일 이름에서 날짜와 시간 표현을 빼도록 명시했습니다. "넣지 마라"보다 "어디에 넣어라"로 쓰고 예시를 함께 주는 방식으로 지시했습니다. 프롬프트를 바꾼 뒤에는 원래 잘 동작하던 문장들을 다시 넣어 시간 해석 등 기존 기능이 깨지지 않았는지 확인했습니다.

**재조정 제안 화면: 제안은 보여주기만 하고, 수락해야 저장한다**
미룬 일정 목록을 화면 위쪽에 보여주고, 일정마다 "제안 받기" 버튼으로 AI 제안과 이유를 표시합니다. 제안은 화면에만 떠 있고, 사용자가 "수락"을 눌러야 `PATCH`로 날짜와 시간이 바뀝니다. "AI는 초안을 만들고 최종 결정은 사람이 한다"는 원칙을 화면 흐름으로 구현한 부분입니다. 일정마다 제안이 다르므로 제안은 일정 id를 키로 하는 객체 상태에 담고, 기존 객체를 고치지 않고 새 객체를 만들어 갱신했습니다. AI 응답을 기다리는 동안에는 해당 버튼을 비활성화해 같은 요청이 중복으로 나가지 않게 했습니다.

**fetch는 4xx, 5xx 응답에서 에러를 던지지 않는다**
fetch는 서버와의 통신이 실패했을 때만 에러를 던지고, 422나 409 같은 응답은 정상적으로 받은 것으로 처리합니다. 그래서 `res.ok`로 상태 코드를 직접 확인하고, 실패하면 백엔드가 보낸 `detail`(예: "AI가 지난 시간을 제안했어요")을 해당 일정 아래에 보여주도록 했습니다.

**데이터를 바꾼 뒤에는 관련 목록을 모두 다시 불러온다**
화면의 목록은 데이터베이스 자체가 아니라 처음에 받아 온 복사본이라, 일정을 완료 체크하거나 삭제해도 미룬 일정 목록에는 그대로 남았습니다. 완료 체크, 삭제, 제안 수락 뒤에 전체 일정과 미룬 일정을 모두 다시 불러오도록 했습니다. 이 과정에서 체크박스가 부르는 `toggleDone` 함수가 작업 중 지워져 있던 것도 발견해 다시 작성했습니다. 처음 미룬 일정이 화면에 뜨지 않았을 때는 백엔드 주소를 브라우저에서 직접 열어 백엔드가 정상임을 확인하고, Network 탭에 요청 자체가 없는 것을 보고 함수를 정의만 하고 호출하지 않았다는 것을 찾았습니다.

**에러 없이 아무것도 표시되지 않은 문제 (`return` 들여쓰기)**
"제안 받기"를 눌러도 에러 메시지도 제안도 나오지 않았습니다. 먼저 주소창에서 직접 연 요청은 GET이라 POST 전용 API에서 405가 나온다는 것을 구분했고, 버튼이 보낸 요청은 Network 탭에서 POST, 200 OK로 정상임을 확인했습니다. `console.log`로 받은 값을 찍어 보니 응답이 `null`이었습니다. 원인은 백엔드의 `return suggestion`이 겹침 검사 `for` 반복문 안으로 들여쓰기되어 있던 것이었습니다. 앞으로 일주일 일정이 없으면 반복문이 돌지 않아 함수가 `None`을 반환했고, FastAPI는 이를 200 OK와 `null`로 응답해 에러가 드러나지 않았습니다. 일정이 있을 때도 첫 번째 일정만 검사하고 반환하는 문제가 숨어 있었습니다. `return`을 반복문 밖으로 옮겨 모든 일정을 검사한 뒤 반환하도록 고쳤고, 같은 함수에서 아직 실행된 적 없던 `statuscode` 오타도 `status_code`로 수정했습니다. 서버가 무엇을 보냈는지(Network 탭)와 코드가 무엇을 받았는지(`console.log`)를 나눠 확인하는 방식으로 원인을 좁혔습니다.

**주간 달성률: 숫자는 코드가 계산한다**
달성률은 정해진 규칙으로 답이 나오므로 AI를 쓰지 않았습니다. 한국 시간 기준 오늘 날짜에서 `weekday()`(월요일 0 ~ 일요일 6)만큼 빼 이번 주 월요일을 구하고, 월요일부터 일요일까지의 일정 중 완료한 비율을 계산합니다. 이번 주 일정이 없을 때 0으로 나누는 에러가 나지 않도록 `round(done / total * 100) if total > 0 else 0`처럼 조건을 먼저 확인합니다. 파이썬은 조건에 해당하는 쪽만 계산하므로 일정이 0개면 나눗셈 자체가 실행되지 않습니다. 이 숫자는 이후 주간 회고 리포트에서 AI가 해석할 재료가 됩니다.
로드맵에서는 아침 알림이 먼저였지만, 알림은 보낼 수단과 서버 상시 실행이 필요해 배포와 묶여 있어 달성률을 먼저 만들었습니다.

**다시 불러올 목록이 늘어나 `refreshAll`로 통합**
달성률이 추가되면서 일정을 추가, 완료 체크, 삭제, 제안 수락할 때마다 다시 불러올 데이터가 전체 일정, 미룬 일정, 달성률 세 가지가 되었습니다. 이전에 완료 체크 뒤 미룬 일정 목록을 다시 불러오지 않은 실수가 있었기 때문에, 세 호출을 `refreshAll` 함수 하나로 묶어 다섯 곳에서 같은 함수를 부르도록 정리했습니다. 불러올 데이터가 늘어나도 한 곳만 고치면 됩니다.

**함수 이름과 API 주소를 혼동해 405 발생**
프론트의 `loadStats` 함수에서 백엔드 주소를 `/schedules/loadstats`로 적어, 요청이 `/schedules/{schedule_id}`(PATCH, DELETE만 허용)로 해석되어 405가 났습니다. 함수 이름은 프론트 안에서 자유롭게 짓지만, API 주소는 백엔드에 등록된 경로(`/stats/weekly`)를 그대로 써야 합니다. 응답을 상태에 담기 전에 `if (!res.ok) return;`으로 실패한 응답을 걸러, 에러 응답이 그대로 들어가 화면에 `undefined%`가 표시되는 일을 막았습니다.

현재 한계: 재조정 제안을 수락하면 일정의 날짜 자체가 바뀌어, 원래 날짜에 하려다 미룬 기록이 남지 않습니다. 미룬 일정이 원래 주의 달성률 계산에서 빠지므로 미룰수록 달성률이 좋아 보일 수 있고, 주간 회고에서 미루는 패턴을 찾을 데이터도 부족합니다. 처음 날짜와 미룬 횟수를 일정에 저장하는 방식과 미룬 기록을 별도 테이블에 쌓는 방식을 검토하고 있습니다.
